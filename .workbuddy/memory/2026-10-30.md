# 2026-10-30

## 完成：CloudIssue 网页版任务看板（Issue Board）

从零搭建完整可运行前后端，位于工作区根目录 `/Users/tianyi/WorkBuddy/cloudissue`。

### 架构分层（职责边界是核心设计点）

```
浏览器 public/  --fetch-->  server/index.js (Express)
                              --MCP stdio-->  mcp-server/index.js
                                                --mysql2-->  MySQL 8 (issue_board)
```

- HTTP 层**不引用** mysql2，所有读写走 MCP tools —— 满足「数据读写通过 MCP 能力完成」。
- `shared/constants.js` 被 Node 与浏览器同时以 ESM 加载，避免前后端枚举文案漂移。
- MCP 以子进程 stdio 方式由 Express 持有单例 Client 连接。

### 数据结构

4 张表：`issues`（主）、`issue_tags`（复合主键去重，支持多标签）、
`issue_status_logs`（append-only 变更日志）、`board_meta`（记录 seeded_at）。
两张子表外键 `ON DELETE CASCADE`，删除任务无孤儿数据。

### 关键实现决策

1. **`afterId` 而非 index**：筛选生效时可见卡片只是子集，索引会在服务端错位；
   "插到某张具体卡片之后"在任何筛选状态下语义唯一。
2. **`position` 服务端重排**：事务内 `FOR UPDATE` 锁定，重排为连续整数，保证并发安全。
3. **失败原因双重校验**：前端拦截只是体验优化，MCP tool 服务端二次校验兜底。
4. **`ensureDatabase()` 独立连接建库**：主连接池指定了 `database`，
   首次启动库不存在时会直接 ER_BAD_DB_ERROR，必须用不带 database 的连接先建库。

### 实测中发现并修复的 bug

1. `server/index.js` 从 `client/stdio.js` 导入了 `StdioServerTransport`（该模块只导出
   `StdioClientTransport`），却按 `StdioClientTransport` 使用 —— 服务启动即崩。改为正确导入名。
2. `issue_create` / `issue_update` 的 `tags` 被约束为 `z.array(z.string())`，
   但前端表单发送的是逗号分隔字符串，被 zod 拒绝（MCP -32602）。
   改为 `z.union([z.array(z.string()), z.string()])` 后由 `normalizeTags` 统一处理。
3. MCP SDK v1.32 中 `McpServer.tool()` 已 deprecated，统一迁移到 `registerTool()`。

### 验证结果

- 环境：Node v22.22.2 / MySQL 8.4.5（官方 tarball 解压到 `/tmp`）/ MCP SDK v1.32.2
- `npm run test:mcp`：7 个 tools 全部注册正常
- `npm test`：32 项断言全部通过，含失败原因强校验、afterId 排序、级联删除、
  以及重启后"保留现有数据"（证明示例数据未重复覆盖用户数据）

### 环境注意事项（重要）

- **Docker Hub 在此网络不可达**（registry-1.docker.io 超时），`docker compose up` 拉取镜像会失败。
- **Homebrew 安装被沙箱阻断**：brew 内部 `sandbox_operation.rb extract` 调用 sandbox-exec 报
  "Operation not allowed"，`brew install` 无法完成。
- 可用替代路径：`curl` 走 `127.0.0.1:51425` 代理可访问 dev.mysql.com，
  直接下载官方 tarball 解压运行 mysqld（基于 `/tmp`，不污染工作区）。
